3Modelo de datos y seguridad

Extensiones y enums

  • postgis en schema extensions; pgcrypto o gen_random_uuid().
  • deal_type: 'rent', 'loan', 'swap'.
  • need_status: 'open', 'matched', 'completed', 'cancelled'.
  • offer_status: 'pending', 'accepted', 'rejected'.

Tablas

TablaCampos principales
profiles id uuid PK → auth.users, full_name, avatar_url, phone, rating_avg numeric(3,2), rating_count, location geography(Point,4326), neighborhood, timestamps.
categories id smallint identity, name, slug, icon, sort_order.
needs id uuid, user_id, title, description, category_id, deal_type, budget_or_offer_details, start_date, end_date, status, reference_image_url, location geography(Point,4326), address_label, timestamps.
offers id uuid, need_id, supplier_id, price_offered numeric(12,2), swap_offered_details, conditions, item_photo_url, status, timestamps, UNIQUE(need_id, supplier_id).
chat_messages id uuid, need_id, offer_id, sender_id, receiver_id, message, created_at.
reviews id uuid, need_id, reviewer_id, reviewee_id, rating smallint 1..5, comment, created_at, UNIQUE(need_id, reviewer_id, reviewee_id).

Índices

  • needs(status, created_at desc), needs(category_id), needs(deal_type), índice GIST en needs.location, needs(user_id).
  • offers(need_id, status), offers(supplier_id).
  • chat_messages(need_id, created_at), reviews(reviewee_id).

4RPCs, triggers, RLS, Storage y Realtime

RPCs transaccionales

FunciónResponsabilidad
set_my_location(lat,lng)Actualiza la ubicación del perfil sin exponer geometría cruda.
create_need(...)Inserta una necesidad construyendo el geography(Point,4326).
nearby_needs(...)Feed cercano con ST_DWithin + ST_Distance, filtros por categoría/tipo/paginación.
accept_offer(offer_id)Valida dueño y pending; acepta una, rechaza las demás y marca need='matched' en una transacción.
reject_offer / cancel_need / complete_needTransiciones de estado controladas y auditables.
send_message(need_id, body)Deriva el receptor desde la oferta aceptada; no confía en receiver_id del cliente.
create_review(need_id, rating, comment)Valida need='completed' y participantes; deriva reviewee_id.

Triggers

  • handle_new_user → crea fila en profiles al registrarse.
  • set_updated_at en tablas mutables.
  • refresh_profile_rating en reviews (insert/update/delete) para recalcular rating_avg y rating_count.

RLS (resumen)

TablaSELECTINSERTUPDATE / DELETE
profilesauthenticatedpropio idpropio
categoriesanon + auth——
needsauthenticated (tablero comunitario)dueñodueño; estados vía RPC
offersproveedor o dueño del needproveedor ≠ dueño y need openproveedor propio pending; aceptación/rechazo vía RPC
chat_messagesparticipantes con oferta aceptadasolo vía RPC—
reviewsauthenticated (reputación pública)solo vía RPC—
Prevención de recursión: helper can_access_chat(need_id, user_id) en security definer; la política de needs es legible por authenticated y no referencia offers.
Privacidad: se guarda ubicación aproximada/barrio, no dirección exacta. Para el MVP las fotos de ofertas van a buckets públicos; la ruta privada con signed URLs queda como mejora.

Storage

  • Buckets públicos: avatars, need-images, offer-images.
  • Escritura solo en {auth.uid()}/...; lectura pública.
  • Subida desde la app con arrayBuffer vía expo-file-system.

Realtime

  • Agregar offers y chat_messages a supabase_realtime; REPLICA IDENTITY FULL para updates.
  • Suscripción en detalle de need (ofertas) y chat con postgres_changes filtrado por need_id.

7Configuración de Supabase

  1. Crear el proyecto en supabase.com y habilitar la extensión PostGIS (Database → Extensions) si el SQL no puede crearla.
  2. Copiar Project URL y anon public key a .env: 
    EXPO_PUBLIC_SUPABASE_URL=https://<ref>.supabase.co
EXPO_PUBLIC_SUPABASE_ANON_KEY=<anon-key>
  3. npx supabase login → npx supabase link --project-ref <ref> → npm run db:push.
  4. npm run db:types para generar tipos.
  5. En Auth → URL Configuration agregar yotengoapp://auth/callback y el redirect de Expo (exp://... en desarrollo).
  6. Google OAuth se configura en Fase 2: client IDs en Google Cloud + provider en Supabase.

8Riesgos y mitigaciones

Expo Go SDK 57Puede no estar en stores; usar Expo Go vía CLI/emulador o un development build con EAS si falla.
Windows / iOSNo hay build iOS local; validación en Android/Expo Go y EAS cuando corresponda.
RLS circularneeds legible por authenticated y helper security definer para chat.
PostGISSi Supabase no permite crear la extensión desde SQL, habilitarla en dashboard y re-ejecutar la migración.
Permiso de ubicación denegadoEl feed cae a “todos los pedidos recientes” sin romper la app.

9Criterio de éxito del MVP

Un usuario publica una necesidad con foto; otro usuario a menos de 5 km la ve, envía una oferta con foto y precio; el creador la acepta; se habilita chat realtime; al completar, ambas partes se reseñan y el rating se actualiza. Todo con RLS verificado y typecheck/lint limpios.

Smoke test de extremo a extremo

  1. Registro con email → perfil creado automáticamente.
  2. Publicar necesidad con foto, fechas y ubicación.
  3. Segundo usuario ve el pedido dentro de 5 km y envía oferta.
  4. Dueño acepta una oferta; las demás cambian a rechazadas.
  5. Chat realtime entre ambas partes.
  6. Completar necesidad → reseñas → rating actualizado.
  7. Verificar con anon key: no puede insertar needs ni leer chats ajenos.
